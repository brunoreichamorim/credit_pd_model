# CLAUDE.md

Working rules for Claude in this repository. For the project overview and roadmap see
[README.md](README.md); for every data and modelling decision see
[docs/decision_log.md](docs/decision_log.md). Do not copy their content here.

## Purpose

A learning project to build skills in credit risk management, Probability of Default (PD)
modelling, programming and working with AI, following sound banking modelling practice.
Correct, transparent and reproducible methodology matters more than maximising accuracy.

## Roles

- **Bruno** is the project owner and the modelling decision-maker.
- **Claude** is a coding and reasoning assistant, not the decision-maker.

**Substantive modelling or data decisions** follow this sequence:

1. Explain the issue and the evidence.
2. Explain the alternatives and their implications.
3. Wait for Bruno's approval.
4. Implement the approved option.
5. Run the tests.
6. Report what changed and the results.

Examples of substantive decisions:
- including or excluding a feature;
- treatment of missing values, zeros or outliers (imputation, indicators, capping, removal);
- data-quality thresholds;
- recoding, merging or dropping categories;
- any change to the split, cross-validation, model type or evaluation metrics;
- anything marked **Open** or **To verify** in the decision log.

If there are several reasonable ways to proceed, stop and present them. Never choose silently.

**Handled directly, without asking first:** routine coding, refactoring, testing, debugging
and documentation that does not change a decision. Keep changes focused and small, and avoid
unnecessary complexity.

## Git rules

- Never commit or push without Bruno's explicit approval.
- Before a commit, check `git status`, then show the changed files, a short summary of each
  change and the full test results.
- Never merge into `main` unless Bruno asks for it.
- Never commit data files. Check that ignored files stay ignored.

## Data rules

- **Raw data:** `data/raw/Loan_Default.csv` is gitignored because its redistribution licence is
  unclear (D-002). Never modify, overwrite or move it; the pipeline only reads it.
- **Processed data:** `data/processed/` (Parquet, DuckDB) is generated by code and gitignored.
- **Artifacts:** only aggregate tables such as `artifacts/dq_*.csv` are committed. Never write
  row-level borrower records to committed files.
- **Cleaning:** add cleaned values as new `_clean` columns next to the raw ones. Never overwrite
  a raw column and never delete rows.
- **Facts:** never invent dataset facts. Verify every number in code against the actual CSV.

## Planned modelling methodology

This methodology is agreed (decision log D-004, D-012, D-013). Do not change it silently.

- Stratified split on `Status` with seed 42:
  - 70% development/training data;
  - 30% final hold-out test data.
- 5-fold cross-validation only within the development/training data.
- All preprocessing is fitted only on training data or training folds, inside a scikit-learn
  `Pipeline` / `ColumnTransformer`, so nothing leaks from validation or test data.
- The hold-out test set is used once, for the final evaluation.
- The primary model is an interpretable logistic regression.
- This is out-of-sample, **not** out-of-time, validation: `year` is constant (2019), so the data
  has no time dimension.
- DuckDB/SQL must do real analytical work in the pipeline, not be decorative.
- Planned evaluation: AUC, Gini, KS, Brier score, calibration, stability/monitoring and risk
  segmentation.

## Critical open issue: possible target leakage

Stage 2 found that `Interest_rate_spread` is missing **exactly** when `Status = 1`. Several
other variables show similar near-perfect separation, for example missing `rate_of_interest`
or `property_value`, and `credit_type = EQUI` (see D-011 and D-017).

- Treat this as a major potential **target-leakage or dataset-construction** issue.
- It must be investigated before any final modelling decision.
- Do not drop, impute, encode, flag or use these variables as features without first
  discussing the implications with Bruno.

## Documentation rules

- Record every important data or modelling decision in `docs/decision_log.md`.
- Give each entry:
  - a **type**: FACT, ASSUMPTION, HEURISTIC or MODELLING CHOICE;
  - a **status**: Agreed, To verify or Open.
- Mark something as FACT only when code in this repository reproduces it.
- Describe heuristic thresholds as heuristics, not as industry or regulatory standards.
- Keep open questions visibly open. Update only the entries affected by new evidence, and do not
  rewrite unrelated ones.
- README: no performance claims or numbers before the code has actually produced them.

## Code conventions

- All paths, seeds, thresholds and column names live in `src/config.py`. No magic numbers in
  other modules.
- Write small, readable functions with type hints and short docstrings that a beginner can
  follow. Match the style of the existing code.
- The data pipeline is `src/data_processing.py`. Extend it rather than duplicating its logic.
- Put tests in `tests/`:
  - unit tests use small synthetic data;
  - tests on the real CSV must skip automatically when the file is absent (as on GitHub).

## Commands

Windows, project virtual environment `.venv`, Python 3.11.9. Run from the repository root:

```
.venv\Scripts\python.exe -m pytest                 # full test suite
.venv\Scripts\python.exe -m src.data_processing    # rebuild processed data and dq_*.csv tables
.venv\Scripts\python.exe -m src.db                 # rebuild the DuckDB database and sql_*.csv tables
.venv\Scripts\python.exe -m src.model               # fit the Stage 5 model and model_*.csv tables
.venv\Scripts\python.exe -m src.holdout             # score the hold-out with the frozen model; validation_*.csv tables
.venv\Scripts\python.exe -m src.grades              # build the Stage 7 illustrative grade scale; grades_*.csv tables
.venv\Scripts\python.exe -m src.monitoring          # Stage 8 baseline and monitoring run; monitoring_*.csv tables
```

- Run the relevant tests after every meaningful code change.
- Run the full suite before proposing any commit.
